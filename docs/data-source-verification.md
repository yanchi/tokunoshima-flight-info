### 実装への影響
- 公開する JSON API・CSV ダウンロードなど、第三者が再利用できる形での提供はしない（第8条第4項(1)）。
- リアルタイム情報には `dc:date` を表示し、`dct:valid` を過ぎたものや同期に失敗したものは「最新」として表示しない。CLAUDE.md §8 の方針とも一致する。
- `/about` `/sources` にガイドライン 3.1 の3点を必ず記載する。
- 許諾終了時に、取り込んだデータを一括削除できる手段（Console コマンド等）を用意する。

### 結論
条件付きOK。公開Webでの表示は可。DB 保存は、問い合わせた構成と保存期間の範囲で可（§9 M1）。再配布の禁止、鮮度・時刻表示、必須の通知を守ること。

### 実装への影響（事務局回答による追加、2026-11-11）
- DB 保存の可否は、問い合わせで示した構成と保存期間を前提とした回答。構成（HTML のみの表示、再利用可能な形で提供しない、トークンをサーバー外に出さない）と保存期間（時刻表は次の取得まで、出発・到着情報は当日分のみで翌日以降に削除）を実装で守る。出発・到着情報の削除を同期処理か定期コマンドで行う。
- 構成や保存期間を変える場合は、この回答の範囲外になるため改めて確認する。

### クレジット表記の決定（2026-11-11、運営者）
- ODPT のデータを表示するときは、ガイドライン 3.1 の例示（§2「通知文の例」）の文面をそのまま使う。「本アプリケーション」は「本サイト」に置き換え、問い合わせ先を書き加える。
- 「日本航空」などのデータ提供者名は、クレジットに併記しない。
- 理由：事務局の回答（§9 M4）は、例示の文面を「原則として」参考にするというものだった。例示の文面には事業者名がない。提供者名を書き足すと、データ提供者が内容を保証しているように見えるおそれがある（基本ライセンス 第4条第2項(6)、CLAUDE.md §6）。また、JAL の社名・商標の扱いは未確認である（§7）。この決定はクレジットの文面に限る。`/sources` の「データ提供元」に ODPT のデータセット名（例：「JAL フライト時刻表」）を書くかどうかは、JAL サイト利用規約での社名・商標の扱い（§7）を確認してから決める。
- 提供者名の併記が必要だと分かった場合は、文言を改める。

### 未確認点（BLOCKED）

- 対応案（要判断）。どの案にも利用者を誤導する境界がある：
  - 案A「運航日の限定を表す備考の便は表示しない」：実際の運航日（12/28、1/1 など）にもその便が表示されなくなる。
  - 案B「備考あり・要公式確認」を付けて時刻表の時刻を表示する：時刻変更の期間中は誤った時刻が主表示になる（例：JL3794 は 11/16-23 に1時間40分早発で、時刻表の時刻と1時間半以上ずれる）。
  - 案C 備考がある便は時刻表の時刻を確定値として目立たせない（時刻欄を「備考参照」にし、備考の原文を表示する）。
- どの案を選んでも、「運航日限定」（例：12/28・1/1）と「時刻変更期間」（例：11/16-23、12/1-1/4）の初日・最終日・期間外の日付を、境界条件として受け入れ基準に書く。
- **決定（2026-10-30、運営者）：案C を採用する。** `odpt:note` がある便は、時刻欄を「備考参照」とし、備考の原文（`ja`）を表示する。備考の内容は機械的に解釈しない。備考の記法が安定していると運用で確認できた場合に限り、解釈して時刻に反映することを改めて検討する。
  - 事務局回答（2026-11-11、§9 M7）：構造化された項目で提供する予定はなく、当面は現状の形式。備考の書式に決まりはない。そのため、備考を解釈して時刻に反映する案は、書式が保証されない前提で検討することになる。案C を当面続ける。
  - 備考を解釈しないため、備考で運航日が限られる便（例：JL2470/2471「12/28・1/1・運航」）も、曜日の時刻表に載っている日はすべて表示対象になる。運航しない日を本サイトが判定することはしない。
  - **表示方法（2026-10-30、運営者決定）：備考がある便は、通常の一覧に混ぜず、一覧の下の「備考のある便」の枠にまとめて表示する。** 通常の一覧には備考がない便だけを並べる。枠の見出しには「運航日が限られる、または期間によって時刻が変わる便です。運航日・時刻は備考と公式情報で確認してください。」の趣旨の説明を付ける（文言は画面実装時に確定）。
  - 受け入れ基準（期待する表示）：備考がある便は、備考の期間内・期間外・初日・最終日のどの日付でも「備考のある便」の枠にだけ表示し、通常の一覧には出さない。各行は便名・区間・時刻欄「備考参照」・備考の原文・運航状況欄「運航状況未確認」とする。期間外の日に便を消したり、時刻表の時刻を表示したりしない。

- 遅延時は `odpt:flightStatus` が `Departed` / `Arrived` のまま、`odpt:flightInformationSummary` に「出発遅延」（en `Delayed`）、`odpt:flightInformationText` に理由（例：「使用する飛行機の到着遅れのため出発に遅延が生じています。」）が入った。**到着便のレコードにも「出発遅延」と入る**（出発地での遅延の説明）。

### 公式時刻表との照合手順（2026-11-11 運営者合意）
§10 の時刻表の自動取得（条件付き Go）の条件を満たすための手順。

1. 対象日：ODPT の時刻表がある期間（初回の照合では 2026-11-11〜2027-01-04。照合し直すときは手順 7 の読み替えに従う）から、次の日を選ぶ。照合する日より前の日付の公式時刻表を閲覧できない場合は、照合する日以降の日付から選ぶ
   - 月〜日の各曜日を少なくとも1日ずつ。時刻表は発・着それぞれ「4路線×7曜日＝28レコード」（計56レコード）なので、56レコードすべてを照合する
   - 備考で時刻が変わる期間の、前日・初日・最終日・翌日（例：JL3794 の 11/15・11/16・11/23・11/24。JL3797 の 11/30・12/1・1/4。JL3797 の最終日 1/4 の翌日 1/5 は、時刻表の期間外のため照合しない）
   - 備考で運航日が限られる日と、その前後の日（例：JL2470/2471 の 12/27・12/28・12/29、12/31・1/1・1/2）
   - `isValidFrom` / `isValidTo` の期間が切り替わる日。2026-11-11 取得のデータでは、照合期間内の便はすべて 2026-10-25〜2027-01-04 の期間で、期間内の切り替わりはない
2. 対象便：TKN 発着の全便（KOJ・ASJ・OKE・ITM の往復）
3. 比べる項目と、一致とみなす基準：
   - 便名・区間：完全に一致すること
   - 出発・到着時刻：分単位で完全に一致すること
   - その日に運航するか：ODPT で運航するとみなせる日（曜日・`isValidFrom/To`・備考から人が読み取った運航日。`isValidFrom/To` は手順 7「有効期間の暦日」と同じ定義で、終了日を含む暦日として読む）の集合が、公式時刻表と一致すること
   - 備考の内容：書き方は違ってよい。備考が示す運航日・時刻の意味が、公式時刻表と一致すること
4. 方法：運営者が JAL 公式サイトの時刻表をブラウザで閲覧して比べる。自動取得・保存・転載はしない。ODPT 側は、便ごとの一覧を用意して照合に使う（一覧は ODPT の生レスポンスから作るため、コミットしない）
5. 記録：この節に、照合日・照合者・照合したデータの `dc:date`（TKN 発・TKN 着それぞれ。レコードの値のうち最も新しい値で、取得の記録と同じ。手順 7）・対象期間・対象日・便数・設定値（照合済みの期間と、方向ごとの照合項目のハッシュ。手順 7）、一致・不一致と不一致の項目を書く。判定の結果は §10 の判断日と根拠の欄にも書き写す。JAL 公式サイトの表示内容は転載しない。ハッシュは手順 7 のコマンドが作るので、記録を書いた時点ではまだない。コマンドの識別子にするコミットに含まれるのはハッシュ以外の項目で、ハッシュは後から別のコミットで書き足す（手順 7「照合し直す流れ」）
6. 判定：すべて一致すれば Go。不一致があれば Go とせず、原因（ODPT の反映遅れ・備考の読み方など）を確かめる
7. 再照合と自動ゲート：照合した結果を設定値にし、同期の処理がこれと比べて公開範囲を自動で決める。人の判断には頼らない。定義はこの手順に一本化し、§10 (2) はここを参照する。この手順で「設定値」は、DB に保存するゲートの値（照合済みの期間とハッシュ）だけを指す。鮮度の閾値は環境変数で与え、「閾値」と呼ぶ（CLAUDE.md §8 の「鮮度の閾値は設定値にする」は、この環境変数で満たす）。
   - 方向の単位：TKN 発（`odpt:originAirport`）と TKN 着（`odpt:destinationAirport`）の時刻表は、別の呼び出しで取得する（§4 検証ログ）。ハッシュ、比較 (a)、外した状態、鮮度の判定は、すべて方向ごとに持つ（2026-11-11 運営者決定）。照合済みの期間は両方向で共通とする（照合は両方向をまとめて行うため）
   - 設定値：照合済みの期間（開始日・終了日）と、方向ごとの、その期間の照合項目のハッシュ。照合に使った取得データ（`dc:date` を記録する）から作り、運営者が設定する。照合したデータと設定値がずれないよう、手順 5 の記録に設定値も書く（ハッシュは後から書き足す。手順 5）。
   - 照合項目：照合済みの期間と重なる便の要素の、便名・区間・要素が入っているレコードの曜日（`odpt:calendar`）・出発／到着時刻・`odpt:originDayDifference`・`odpt:destinationDayDifference`・`isValidFrom`・`isValidTo`（原文の日時ではなく暦日。下記「有効期間の暦日」）・`odpt:note`（日本語 `ja` の原文だけ。ほかの言語の本文は照合項目に含めない。2026-11-12 運営者決定）。`odpt:airline` も照合項目に含める（2026-11-11 運営者決定。§8 申し送りで、`odpt:airline` は原文のまま保持すると決めているため。照合項目をここで確定させ、ハッシュの計算方法を後から変えずに済むようにする）。画面に表示する時刻表の項目は、照合項目に含まれるものに限る。照合項目に含まれることは表示できる条件の一つで、表示してよい理由にはならない（`odpt:airline` は §4「実装への影響」のとおり表示しない）。対象は便の要素とレコードの項目で、取得元・出典の表示と、取得の記録の取得日時は含まない。照合項目にない項目（`odpt:aircraftType` など）は保存しない（画面に出すと、照合していない内容が (a) で検知されないまま公開されるため）。表示する項目を増やすときは、照合し直す前提で、照合項目・ハッシュの計算方法・保存する列を合わせて変える。`isValidFrom` / `isValidTo` は照合済みの期間で切り詰めてから比べる。照合済みの期間と重ならない要素は対象にしない。項目がない場合と、項目の値が null の場合（例：今のデータにない dayDifference）は、どちらも null として扱い、推測で 0 を入れない（CLAUDE.md §5。値が null の場合は 2026-11-12 運営者決定）。後から ODPT が 0 を出すようになると (a) が起きるが、安全側の挙動として許容する。照合済みの期間のうち過ぎた日付の要素も対象に残すため、ODPT が期限の過ぎた要素を消すと、それだけで (a) が起きて照合済みの期間全体が外れる。これも安全側の挙動として許容する。ハッシュの計算方法（並び順・正規化など）は実装で決め、固定の入力と期待するハッシュを持つテスト（golden test）で固定する。計算方法は変えない（2026-11-11 運営者決定。変えると、デプロイ直後の同期で両方向とも (a) が起き、照合し直すまで公開できなくなるため）。どうしても変えるときは、照合し直す前提で運営者が判断する。
   - 公開範囲：方向ごとに、照合済みの期間とする。(a) で外した方向は空になる。
   - 比較 (a)：方向ごとに、照合済みの期間の照合項目が変わったか。変わったら、その方向の照合済みの期間全体を公開範囲から外し、照合し直す。もう一方の方向は公開を続ける。
   - 比較 (b)：照合済みの期間の外のデータが変わったか（増えた、`isValidTo` が照合済みの期間の終了日以降で短くなった、など）。公開範囲はもともと照合済みの期間に限られるので、変わった分は公開されない。(b) で行うのは同期ログへの記録だけで、照合済みの期間はそのまま公開を続ける。
   - (a) と (b) が同時に起きた場合は、(a) を優先する（その方向の照合済みの期間を外す）。
   - (a) で外した状態は、照合し直して設定値を置き換えるまで解除しない。その後のデータが照合したときの内容に戻っても、自動では公開に戻さない（2026-11-11 運営者決定。照合し直していない状態で公開を再開しないため）。外した状態は、設定値の版と組にして、同期の処理が永続的に保存する。前回の取得データは残さないため、毎回の比較だけからは導けないことによる。解除するのは、照合し直して手順 5 に記録し、設定し直したとき。設定し直した値が前と同じでも解除する（2026-11-11 運営者決定。照合し直して同じ内容だと分かる場合があるため）。保存先と解除の操作は、下記「設定値と外した状態の保存・解除」に従う。
   - `dc:date`：変わったら、照合し直す合図として同期ログに記録する。`dc:date` が変わっただけでは公開を止めない（2026-11-11 運営者決定。中身の変化は (a)(b) で検知できるため）。
   - 設定値がない場合（最初の照合の前）：どの日付も公開しない。
   - 保存するデータ：検証を通った取得データの全レコードを、方向ごとに保存する。保存する項目は照合項目に限る（上記「照合項目」）。1件でも検証・マッピングに失敗したレコードがあれば、その方向の取得は保存せず、失敗として扱う。失敗したレコードだけを除いて保存することはしない（便が欠けた時刻表を、コマンドが `dc:date` の一致だけで設定してしまうため）。公開範囲で絞るのは表示するときに行う（保存するときに絞ると、最初の設定でハッシュを作れないため）。それより前の取得データは残さない（M1 で可とされた保存期間は「時刻表は次の取得まで」）。
   - 検証・マッピングで失敗とする条件（2026-11-12 運営者決定、PR #17）：次のどれかに当たると、その方向の取得全体を失敗とする（上記「保存するデータ」）。失敗は同期ログに記録し、同期は終了コード 1 で終わる（下記「同期の終了コード」）。推測で読み替えて取り込むより、取り込まずに気づける方を選ぶ（CLAUDE.md §2）
     - 応答全体：JSON の配列でない。0件。件数が静的データの上限（1000件。§1）に達している（途中で切れている可能性があるため）。全レコードを合わせて便の要素が0件
     - レコード：`@type` が `odpt:FlightSchedule` でない。`odpt:operator` が `odpt.Operator:JAL` でない。方向の空港（TKN 発なら `odpt:originAirport`、TKN 着なら `odpt:destinationAirport`）が TKN でない。`odpt:calendar` が月〜日の7つ以外（祝日などの値。§5 の確認では曜日以外の値はなかった）。区間と曜日が同じレコードが重複している。`odpt:flightScheduleObject` がない、または配列でない（キーがないことを「便なし」とは読まない）。1つのレコードだけ便の要素が空配列なのは許す（曜日によって便のない路線があり得るため）
     - 便の要素：便名が1つでない（共同運航。検証済みのデータにはなく、表示の仕方が決まっていない）。便名・時刻（`HH:MM`、00:00〜23:59）の形式が違う。`isValidFrom` / `isValidTo` がない（「期間の制限なし」と推測しないため）、`isValidFrom` の時刻が `00:00:00` でない、`isValidTo` の時刻が `23:59:59` でない（下記「有効期間の暦日」）、または `isValidFrom` の暦日が `isValidTo` の暦日より後。同じレコードの中で、同じ便名の有効期間が重なる（同じ日に同じ便が2つの時刻で載り、どちらが正しいか決まらないため。境界の1日だけ重なる場合も失敗。期間が切り替わるだけ（終了日の翌日から次の期間が始まる）なら許す）。前後関係と重なりは、JST の暦日どうしで、開始日・終了日を含めて比べる（下記「有効期間の暦日」）。便名が違う便は、一日に何本あっても重なりの判定の対象にならない。dayDifference が整数でも null でもない。`odpt:note` があるのに日本語（`ja`）の本文がない、空、または空白だけ。`odpt:note` の値が null の場合も失敗にする（dayDifference の null は「値がない」と読めるが、note は項目があるのに本文がない形になり、備考がないのか欠けたのか決まらないため）。`odpt:airline` がない、または空文字
     - 日時（`dc:date`・`isValidFrom`・`isValidTo`）：タイムゾーンがない。オフセットが `+09:00` 以外（`Z` も含む。2026-11-12 運営者決定、PR #17。検証済みのデータはすべて `+09:00` で、受け付ける形を推測で広げないため。`isValidFrom` / `isValidTo` は、下記「有効期間の暦日」でも、ほかのオフセットを受け付けないと決めた。`dc:date` は暦日に直さず時点として扱う値で、`+09:00` 以外を受け付けるかは見直していない。下記「未確認点」）。形式が秒まで（`YYYY-MM-DDTHH:MM:SS+09:00`）でない（小数の秒も受け付けない）。存在しない日付（例：02-30）
     - 上のほか、必須の項目（`dc:date`、空港、`odpt:calendar`、便名、時刻、`isValidFrom` / `isValidTo`、`odpt:airline` など）がない場合、型が違う場合（レコードや便の要素がオブジェクトでない、文字列であるべき値が文字列でない、など）、TKN でない側の空港が `odpt.Airport:<IATA 3レターコード>` の形式でない場合も、すべて失敗とする
     - 帰結：ODPT 側でこのどれかに当たる変更があると（例：祝日のレコードが1件加わる）、コードを直すまでその方向の取得は失敗し続ける。最後に保存できたデータの表示は続くが、警告の閾値（初期値3日）を超えると警告を出し、公開停止の閾値（初期値7日）を超えるとその方向の時刻表の公開が止まる（下記「時刻表の鮮度の閾値」）。運営者は同期ログと cron の終了コードで気づき、仕様を決めてからコードを直す
   - 有効期間の暦日（2026-11-12 運営者決定、PR #22）：`isValidFrom` / `isValidTo` は、次の定義で JST の暦日に直して扱う。この定義は ODPT の仕様書に基づくものではない（§3 の仕様書の記載は「適用期間」だけで、暦日や終了日の扱いは定義されていない）。§5 の実データ（`dc:date` 2026-08-21T13:00:00+09:00 の版）の形から、運営者が判断した。取り込み時の前後関係・重なりの判定、保存、照合済みの期間で切り詰める処理、ハッシュの計算は、すべてこの暦日を使う
     - 暦日への変換：`+09:00` の日時の日付部分を、そのまま暦日とする（例：`2026-10-25T00:00:00+09:00` → 2026-10-25）
     - 終了日：含む。`isValidTo` が `2027-01-04T23:59:59+09:00` なら、2027-01-04 まで有効
     - 時刻部分：`isValidFrom` は `00:00:00`、`isValidTo` は `23:59:59` のときだけ受け付ける。ほかの時刻は取り込み失敗とする（一日の途中で始まる・終わる期間で、その日を期間に入れるかを推測しないため。CLAUDE.md §2）
     - オフセット：`+09:00` だけを受け付ける（上記「日時」）
     - 帰結：ODPT がこの形に合わない値を出すと、コードを直すまでその方向の取得は失敗し続ける（上記「帰結」）。安全側の挙動として許容する
     - 保存：暦日として保存する（日付の列。時刻とタイムゾーンを持たない）。この定義の前に保存したデータは、マイグレーションで日付に直す。有効期間の時刻が `00:00:00` / `23:59:59` でない行が1件でもあれば、マイグレーションは中止する（日付に丸めて残さないため）。そのときは時刻表の保存データと取得の記録を空にして、取得し直す
   - 取得の記録：方向ごとに「最後に保存できた取得」の記録を持つ。項目は、取得日時・`dc:date`・件数。取得日時は要求を開始した時刻（UTC）で、リトライしたときは最初の試行の開始時刻とする（安全側）。秒単位で、端数を切り捨てて保存する（経過時間が最大1秒長くなるだけで、警告・公開停止が早まる方向にしか働かない。下記「古い取得による置き換え」）。`dc:date` は、レコードの `dc:date` のうち最も新しい値とする（暫定。下記「未確認点」の `dc:date` の項目が分かったら見直す）。鮮度の判定と、コマンドでの `dc:date` の照合は、この記録を使う。便の行の `FlightSchedule.fetched_at` は使わない（行ごとに値が違う場合に、どの値を起点にするか決まらないため）。
   - 同期のトランザクション：同期は、方向ごとに、取得データの置き換え・取得の記録の更新・比較 (a)(b)・外した状態の記録を1つのトランザクションで行う。どれかが失敗したら、すべて確定しない（CLAUDE.md §8）。データと取得の記録がずれると、鮮度の判定とコマンドの照合が間違ったデータを見るため。
   - 表示に使うデータ：保存されている最新の取得データを、公開範囲に絞ったもの。取得・検証・マッピングに失敗して保存しなかったときは、最後に保存できたデータを取得日時付きで表示し続ける（CLAUDE.md §8）。このときも、最後に保存できたデータにゲートをかけた公開範囲だけを表示する。失敗が長く続いた場合は、下記「時刻表の鮮度の閾値」に従う。
   - 時刻表の鮮度の閾値（2026-11-11 運営者決定、GitHub Issue #11）：
     - 閾値は2段階とし、どちらも環境変数で与える。運航状況の鮮度の閾値とは別の環境変数にする（§8「画面実装への申し送り」）。単位は秒とする
       - 警告の閾値：初期値3日（259200秒）。超えたら、取得日時と「最終取得から時間が経過しています」を表示する。表示は続ける
       - 公開停止の閾値：初期値7日（604800秒）。超えたら、その方向の時刻表の公開を止める。通常の一覧も「備考のある便」の枠も、公開範囲の外の日付と同じく出さない。`/flights` でもその方向の日付を案内しない（下記「公開範囲の外の日付」）。ただし最低条件として、最後に取得した日時と公式運航情報の案内文を表示し（取得日時が未来の場合を除く。下記「判定の基準」）、提供範囲の外と同じ表示だけにはしない（CLAUDE.md §6・§8。取得できていないことを利用者に示すため）。(a) で外すこととは別の状態として扱う（(a) は照合し直すまで戻らず、公開停止は取得に成功すると戻る）。停止中に表示する文言は、画面を実装するときの仕様で決める（§8「画面実装への申し送り」）
       - 閾値の制約：0 < 警告の閾値 < 公開停止の閾値 ≤ 7日（604800秒）。上限の7日はコードの定数とし、環境変数では変えられない
       - 無効な閾値：未設定、数値でない、0以下、上の制約を満たさない場合は、どれも無効とする。無効なときは、時刻表をどの日付も公開しない。時刻表の鮮度の判定は例外を投げず、「公開不可」として返す。運航状況の表示と、`/about` `/sources` などの静的ページは表示を続ける（既存の `FreshnessPolicy` はコンストラクタで例外を投げるので、同じ作りにすると、サイト全体がエラーになるため）。無効なときの表示は、公開を止めている間と同じにする。一度も取得していない（取得の記録がない）ときは、閾値の有効・無効にかかわらず設定値も作れないので何も公開しない。そのときに表示する文言は、画面の仕様で決める
       - 閾値の読み方：環境変数は文字列として受け取る。`%env(int:...)%` は使わない（未設定や数値でない値で、サービスを作る段階で例外が出るため）。未設定に備え、`env(...)` の既定値を空文字にする（`config/services.yaml` の `env(CONTACT_ADDRESS)` と同じ方法）。数値への変換と検証は判定のコードで行い、受け付ける形式は `\A[1-9][0-9]*\z` に限る（PHP の `^...$` は末尾の改行の直前にも一致するため、`\A` と `\z` を使う。`" 259200"`、`"1e5"`、`"259200.0"`、`"+259200"`、`"259200\n"` は無効）。同期のコマンドは、閾値が無効でも例外で止まらず、取得と保存を続ける（データの鮮度は保つ）。閾値が無効なことは、同期のたびにエラーとして記録する。`app:check-deploy-config` も同じ検証のコードを呼び、判定の基準を一か所にまとめる
     - 判定の基準：方向ごとの「取得の記録」の取得日時から、表示する時点までの経過時間。暦日（JST）では数えず、経過した秒数で比べる。経過時間 ≤ 閾値のときを閾値以内とする。取得日時が表示する時点より未来の場合は、時計のずれか不正なデータとみなし、公開停止として扱う。このときは取得日時を表示せず、「取得日時を確認できません」などと表示する（誤った鮮度を見せないため。CLAUDE.md §2。文言は画面の仕様で決める）。表示する処理は同期ログを書かない。同期の処理が、開始するときに取得の記録と `ClockInterface` の現在時刻を比べ、未来なら同期ログに記録する（既存の `FreshnessPolicy::isFresh` が未来の時刻を信用しないのと同じ趣旨）。現在時刻は `ClockInterface` から得る。片方だけが警告の閾値を超えたときは、その方向の画面だけに警告を出す。片方だけが公開停止の閾値を超えたときは、その方向の時刻表だけ公開を止める
     - 判定は表示するときに行う。同期の処理が止まっていても（cron やコンテナの停止など）、公開停止の閾値を超えれば公開が止まる。HTTP キャッシュやページキャッシュの有効期間が、この判定を遅らせないようにする
     - デプロイ前チェック（`app:check-deploy-config`）でも閾値を検証する。ただし、このチェックはデプロイ手順にもコンテナの起動時にもまだ組み込まれていない（GitHub Issue #6）。実行時の判定を主とし、チェックは補助とする
     - 公開停止の閾値を7日以下にする理由：ガイドライン 2.2.1・2.2.2 は、センターの更新通知から1週間以内の反映を求めている（§8）。最後に取得できてから7日以内に公開を止めれば、その後に来た更新通知についても、運営者が対応しなくても1週間以内に古い内容を表示しなくなる。§8 の整理と同じく、公開を止めることが「反映」に当たるとするのは本サイト側の解釈で、ODPT には確認していない（下記「未確認点」）。最後に取得できる前に来た更新通知は、その取得で反映されている前提とする
     - 取得・保存に成功すると、その方向の警告と公開停止は自動で解除される。新しい取得データにも手順 7 のゲートをかけ、公開範囲を決め直す。(a) で外した状態は、この自動解除では解除しない
     - 時刻表だけの便は、閾値の内外に関係なく「運航状況未確認」と表示する（CLAUDE.md §6）
     - 運営者が気づく方法：取得・検証・マッピングの失敗は、その都度、同期ログに失敗として記録する。警告の閾値を超えている間は、同期を実行するたびに閾値超過をエラーとしてログに記録する。公開停止の閾値を超えている間は、警告の閾値超過と区別できる形で、公開停止として記録する。閾値が無効なときも、同期のたびにエラーとして記録する。運営者は同期ログの確認で気づく（確認の頻度は下記「運営者の確認」）。同期の処理そのものが止まった場合はログが残らないため、外から検知する方法（ヘルスチェックで取得の記録からの経過を返すなど）は、公開前に決める（§10「公開前の確認事項」）
   - 設定値と外した状態の保存・解除（2026-11-11 運営者決定、GitHub Issue #12）：
     - 保存先：設定値（照合済みの期間・方向ごとのハッシュ）と外した状態は、DB に保存する。設定ファイルや環境変数には置かない。同じ値を書き直しても、変化として検知できないため
     - 設定する操作：最初の設定と、設定し直すときのどちらも、同じ Console コマンドだけで行う。1回の実行で、両方向の設定値をまとめて新しい版にする
     - コマンドの必須の入力と形式：
       - 照合済みの期間（開始日・終了日）：JST の暦日で、終了日を含む。開始日 ≤ 終了日でなければならない
       - 照合した日：JST の暦日
       - 手順 5 の記録の識別子：手順 5 の記録を main に入れた PR の、マージコミットのハッシュ。40桁の小文字の16進数（`\A[0-9a-f]{40}\z`。末尾に改行が付いた値も受け付けない）に限り、それ以外は受け付けない。マージコミットは main の履歴に必ず残るので、後からたどれる。リポジトリの設定で squash・rebase によるマージは無効にしてある（2026-11-11 設定）
       - 照合に使った取得データの `dc:date`：TKN 発と TKN 着の取得ごとに1つずつ。時点（タイムゾーン付きの日時）として比べ、DB に保存する。タイムゾーンのない値（例：`2026-08-21T13:00:00`）は、形式が違うとして受け付けない
       - 照合済みの期間は、両方向の保存データの範囲（`isValidFrom` の最小〜`isValidTo` の最大。暦日で、両端を含む）に含まれなければならない。データのない日付を照合済みとして公開しないため
       - どれかが欠けたとき、形式が違うときは設定しない
     - コマンドは、方向ごとに、ハッシュを、保存されている最新の取得データから同期の処理と同じ実装で作る。方向ごとの「取得の記録」の `dc:date` が入力と違うときは、照合したデータと保存されているデータが違うので、設定しない。1回の取得の中でレコードごとに `dc:date` が違う場合に、どの値と比べるかは未確認（下記「未確認点」）。それが分かるまでは、取得ごとのレコードの `dc:date` のうち最も新しい値と比べる（暫定）。片方の方向の取得が失敗していても、両方向とも保存されている最新の取得データでハッシュを作る。どちらかの方向に取得の記録がない（一度も保存できていない）ときは、設定しない
     - コマンドが確かめるのは、識別子の形式だけとする。そのコミットが存在し、手順 5 の記録を含むことは確かめない（本番のコンテナには検証記録とその履歴を置かないため）。照合し直して手順 5 に記録してからコマンドを実行することは、運営者の手順で担保する（2026-11-11 運営者決定。このため、Issue #12 の受け入れ基準「手順 5 の記録なしに同じ値を再適用した場合は外したままにする」は、システムでは満たさず、下記「運用上の確認」で満たす）
     - 記録：検証をすべて通って設定したときだけ、入力した値と作ったハッシュ、実行日時を、設定値の新しい版として DB に保存する。検証に通らなかった実行は版を作らない。外した状態は方向ごとに、比較に使った版の ID と組にして保存し、新しい版を設定したときに解除する
     - 並行実行：コマンドは、`dc:date` の照合からハッシュの作成、版の保存までを1つのトランザクションで行う。同期の処理は、比較に使った版の ID を指定して外した状態を記録する（比較の後に新しい版が設定されていたら、古い版に対する外した状態として扱われ、新しい版には影響しない。下記のロックで直列にしているため通常は起きないが、念のための保護として残す）。同期とコマンドは、アプリの中で同じ名前のロックを取り、同時に動かないようにする（運営者が手で実行するコマンドには、cron の `flock` が効かないため。ライブラリ（Symfony Lock など）は未導入で、導入は実装するときに決める）。cron の `flock` は、同期の多重起動を防ぐ補助とする
     - ロックの範囲と、取れなかったとき：同期のロックの範囲は、取得の後の検証から DB の確定まで（API の呼び出しはロックの外）。設定のコマンドと手動で外す操作は、版の読み込みから DB の確定までをロックの中で行う。ロックは1つの名前で、同期・設定のコマンド・手動で外す操作のすべてが取る。同期は、方向ごとのトランザクションのたびに取る（方向ごとに取得と確定を行うため）。ロックが取れなかったときは待たずに失敗する。設定のコマンドと手動で外す操作は、終了コード 1 で終わり、何も変えない。同期はその方向をスキップしたことを同期ログに残し、1つでもスキップしたら終了コード 1 で終わる（cron の監視で気づけるようにするため）。本番のコンテナは1台を前提とする（未確認。複数台にするときは、ロックの保存先を見直す）
     - 同期の終了コード：次のどれかに当たった回は、終了コード 1 で終わる。どれにも当たらなければ 0。(1) どれか1方向でも保存できなかった（取得・検証・マッピングの失敗、0件、ロックによるスキップ）、(2) 閾値が無効、(3) 取得日時が未来の取得の記録を検知した。API の障害を cron の監視で見逃さないため。取得と保存に成功した回は、その方向の警告・公開停止が解除されるので、閾値超過では 1 にしない
     - 古い取得による置き換え：保存されている取得の記録より取得日時が古い取得では、データも取得の記録も置き換えない（運営者が手で同期を実行して cron の同期と重なったとき、先に始めた取得が後から確定して、新しいデータを古いデータで上書きしないため）。置き換えなかったことは同期ログに残す。取得日時は秒単位で、端数を切り捨てて保存する（データが実際より新しく見えないようにするため）。保存されている取得と同じ秒に始まった取得は、前後を決められないので置き換えない（保存されている方を残す）
     - 手動で外す操作：照合し直す途中などで、まだ公開中の方向に公式時刻表との不一致が見つかったときのため、同じ Console コマンドに、方向を指定して公開範囲から外す操作を設ける（2026-11-11 運営者決定）。入力は方向と理由で、必須とする。設定値の版が一つもないとき（最初の設定の前）は、何も公開していないので、外す操作は何もせず終了コード 1 で終わる。外した状態は、実行した時点で有効な版の ID と組にして保存し、(a) で外した場合と同じく、照合し直して新しい版を設定するまで解除しない。操作の記録（実行日時・方向・理由）は、外した状態と一緒に DB に保存する（同期の処理ではないので、同期ログには書かない）
     - 照合してからコマンドを実行するまでの間に、同期で取得データが置き換わり `dc:date` が変わった場合は、設定できない。照合し直す。保存期間が「次の取得まで」（M1）で、照合したデータを残しておけないため
     - 公開停止の閾値を超えている間にコマンドを実行した場合：`dc:date` が一致すれば設定できる。ただし鮮度の判定で公開停止のままで、次に取得・保存に成功したときに、新しい取得データにゲートをかけて公開範囲を決める
     - コマンド名・テーブルの構成は実装で決める
   - 公開範囲の外の日付：通常の一覧も「備考のある便」の枠も出さない。公式運航情報の案内文は出す。`/flights` で案内する日付は公開範囲に限る。表示する文言と、理由（提供範囲の外・照合待ち・中身が変わって外した期間）を利用者に区別して見せるかどうかは、画面を実装するときの仕様で決める（2026-11-11 運営者決定）。
   - 受け入れ基準（期待する表示）：
     - 新しい期間が足されただけ：照合済みの期間は表示を続け、新しい期間は公開しない
     - 照合済みの期間の時刻が変わった：その方向の照合済みの期間を公開範囲から外す
     - 照合済みの期間の備考だけが変わった：その方向の照合済みの期間を公開範囲から外す
     - TKN 発の照合済みの期間だけが変わった：出発の照合済みの期間を公開範囲から外す。到着は表示を続ける
     - `isValidTo` が延びただけ：照合済みの期間は表示を続け、延びた分は公開しない
     - `dc:date` だけが変わった：表示を続け、同期ログに記録する
     - 設定値がない：どの日付も公開しない
     - 取得に失敗した：最後に保存できたデータを、ゲートをかけた公開範囲に限り、取得日時付きで表示し続ける（閾値の扱いは下記）
     - 取得したレコードの一部だけが検証・マッピングに失敗した：その方向の取得は保存せず、取得に失敗した場合と同じに扱う
     - 取得したデータが上記「検証・マッピングで失敗とする条件」に当たる（例：祝日のレコードが加わった、共同運航で便名が2つある、同じ便名の有効期間が重なる）：その方向の取得は保存せず、取得に失敗した場合と同じに扱う。同期ログに理由を残し、終了コード 1 で終わる
     - 1つのレコードだけ便の要素が空配列で、ほかのレコードに便がある：保存する
     - 取得が0件だった：時刻表の取得としては異常（§8 申し送り）として保存せず、取得に失敗した場合と同じに扱う
     - 照合済みの期間内で、便が増えた・減った：その方向の照合済みの期間を公開範囲から外す（(a)）
     - 運航曜日が変わった（要素が別の曜日のレコードへ移った）：その方向の照合済みの期間を公開範囲から外す（(a)）
     - 照合済みの期間と一部だけ重なる新しい要素が来た（例：新しい要素は 12/20 から、古い要素は 12/19 まで）：その方向の照合済みの期間を公開範囲から外す（(a)。重なる要素の集合が変わるため）
     - `isValidTo` が、照合済みの期間の終了日より前に短くなった：その方向の照合済みの期間を公開範囲から外す（(a)）
     - `isValidTo` が、照合済みの期間の終了日以降に短くなった（終了日ちょうどを含む）：照合済みの期間は表示を続ける（切り詰めると (a) にならない。(b) として同期ログに記録する）
     - (a) と (b) が同時に起きた：その方向の照合済みの期間を公開範囲から外す（(a) を優先）
     - (a) で外した後に、データが照合したときの内容に戻った：外したままにする。照合し直して設定値を置き換えるまで公開しない
     - (a) で外した後に、照合し直して手順 5 に記録し、コマンドで前と同じ値を設定し直した：公開を再開する
     - (a) で外した後に、設定値に手を触れていない：外したままにする
     - (a) で外した後に、照合済みの期間・照合した日・手順 5 の記録の識別子・`dc:date` のどれかを入力せずにコマンドを実行した：設定せず、外したままにする。版も作らない
     - 識別子が40桁の小文字の16進数でない（大文字を含む場合も）：設定せず、外したままにする
     - 開始日が終了日より後：設定しない
     - 照合済みの期間が、保存データの範囲を超える（例：データは 2027-01-04 までなのに、終了日を 2027-03-31 と入力した）：設定しない
     - どちらかの方向に取得の記録がない：設定しない。版も作らない
     - `dc:date` の入力にタイムゾーンがない：設定しない
     - 照合し直す途中で、公開中の TKN 発に不一致が見つかり、コマンドで TKN 発を手動で外した：出発の時刻表を公開しない。データが変わらなくても外したままにし、照合し直して新しい版を設定したときに解除する
     - 方向か理由を入力せずに手動で外す操作を実行した：何もせず、終了コード 1 で終わる
     - 設定値の版がないときに手動で外す操作を実行した：何もせず、終了コード 1 で終わる
     - 設定のコマンドと手動で外す操作が同時に実行された：後から実行した方はロックが取れず、終了コード 1 で終わる。外した状態が古い版に結び付いて黙って消えることはない
     - 照合項目にない項目（例：`odpt:aircraftType`）：画面に表示しない
     - コマンドに入力した `dc:date` が、保存されている取得データの `dc:date` と違う（TKN 発・TKN 着のどちらか一方でも）：設定せず、外したままにする
     - 手順 5 の記録なしに、形式の正しい識別子で同じ値を設定し直した：システムでは防げず、解除される。下記「運用上の確認」で防ぐ（2026-11-11 運営者決定。Issue #12 の基準を変えた）
     - 設定値がない状態で、必須の入力をそろえてコマンドを実行した：設定し、照合済みの期間を公開する
     - TKN 着の取得が API の障害で失敗し、TKN 発は保存できた：TKN 発だけ置き換え、同期は終了コード 1 で終わる
     - 運営者が手で実行した同期と cron の同期が重なり、先に始めた取得が後から確定しようとした：置き換えず、同期ログに残す
     - ロックが取れなかった：コマンドは終了コード 1 で終わり、何も設定しない。同期はその方向をスキップして同期ログに残し、終了コード 1 で終わる
     - コマンドの実行中に同期が新しい外した状態を記録しようとした：アプリの中のロックで、同期とコマンドは同時に動かない。直列にした結果、外した状態は比較に使った版にだけ結び付く
     - 同期の途中（データの置き換えの後、取得の記録の更新の前など）で失敗した：どれも確定せず、前回の取得データと取得の記録が残る
     - 公開停止の閾値を超えている間に、コマンドで設定した：設定はされるが、公開停止のまま。次に取得・保存に成功したら、ゲートをかけた公開範囲を表示する
     - 取得の失敗が続き、最後に保存できた取得日時から警告の閾値以内：公開範囲を取得日時付きで表示し、経過の警告は出さない
     - 取得の失敗が続き、警告の閾値を超え、公開停止の閾値以内：公開範囲の表示は続け、取得日時と「最終取得から時間が経過しています」を表示する。同期のたびに閾値超過をエラーとしてログに記録する
     - 取得の失敗が続き、公開停止の閾値を超えた：その方向の時刻表の公開を止める。一覧は出さず、最後に取得した日時と公式運航情報の案内文を表示する。提供範囲の外と同じ表示だけにはしない。同期のたびに公開停止として、警告の閾値超過と区別してログに記録する
     - 同期の処理が止まったまま（同期ログも残らない）、公開停止の閾値を超えた：表示するときの判定で、公開を止める

     - TKN 発だけが公開停止の閾値を超えた（TKN 着は取得できている）：出発の時刻表だけ公開を止める。到着の画面は通常どおり表示する
     - 閾値を超えた後に、取得・保存に成功した：その方向の警告と公開停止を解除する。新しい取得データにゲートをかけた公開範囲を表示する。(a) で外した状態は解除しない
     - 経過時間が閾値ちょうど：閾値以内として扱う（例：警告の閾値 259200秒ちょうどなら警告を出さず、259201秒なら出す。公開停止の閾値は 604800 なら有効、604801 なら無効）
     - 取得日時が表示する時点より未来：公開停止として扱い、取得日時は表示しない。同期の処理が、開始するときに同期ログに記録する
     - 閾値が無効（例：公開停止の閾値が8日、警告の閾値が公開停止の閾値以上、未設定、数値でない、0以下、`"1e5"` や `" 259200"`）：時刻表をどの日付も公開せず、公開を止めている間と同じ表示にする。運航状況の表示と静的ページは表示を続け、エラーにならない。同期のコマンドも例外で止まらず、取得と保存を続けたうえで、エラーとしてログに記録する。デプロイ前チェックは失敗する
   - 運営者の確認：公開範囲から外したこと、外にデータが増えたこと、照合済みの期間の外のデータが変わったこと（`isValidTo` が終了日以降で短くなった場合など）、`dc:date` が変わったこと、時刻表の鮮度の閾値を超えたこと、公開を止めたこと、閾値が無効なこと、取得日時が未来になっていることは、同期ログに記録する。運営者が同期ログを確認する頻度は、運用を始めるまでに決める。利用者へのメールやプッシュ通知はしない（画面上の警告は上記の閾値に従って出す）。
   - 運用上の確認（コマンドでは保証しない）：

     - 時刻表の再取得の間隔（cron）が、警告の閾値の半分以下になっていることを確かめる（§8。cron の間隔はアプリから見えず、自動のテストでは確かめられないため）
     - 手順 5 の記録なしに、同じ値をコマンドで設定し直さない。識別子のマージコミットが main にあり、手順 5 の記録を含むことを、運営者がコマンドの実行前に確かめる
   - 照合し直す流れ（最初の照合も同じ）：
     1. 新しい取得データの期間全体で、手順 1〜6 をやり直す。手順 1 の対象期間と例は、新しいデータの期間に読み替える（例：2027-01-05 からの期間が加わったら、その初日の 1/5 も照合の対象になる）

     3. その PR のマージコミットに、手順 5 の記録が含まれることを確かめる（上記「運用上の確認」）
     4. 上記「設定値と外した状態の保存・解除」のコマンドで、設定値（照合済みの期間と方向ごとのハッシュ）を置き換える。識別子は手順 2 のマージコミットのハッシュにする。ハッシュはコマンドが、照合に使った取得データから同期の処理と同じ実装で作る。照合したデータと設定値がずれないようにするため
     5. コマンドが作ったハッシュを、別のコミットで手順 5 の記録に書き足す。このコミットは識別子にしない

## 8. 鮮度・更新頻度の方針（確認後に記入）

- 同期間隔：未定。ガイドライン 2.1.2 は `odpt:frequency` の間隔での更新を求めている。航空系の応答には frequency がなく、事務局回答で `dct:valid`（約7分後）を更新間隔の目安にしてよいとされた（§3、§9 M5）。具体的な間隔は、呼び出し回数の上限（IP 単位。§1）と運航時間帯に限るかどうかを含めて決める
- 運航状況（動的データ）の「最新」とみなす鮮度閾値：未定。`dct:valid` を超えたデータは表示しない（ガイドライン 2.1.2）
- 時刻表（静的データ）の再取得の間隔：未定。ガイドライン 2.2.1 の「定期的に再取得」に当たる。警告の閾値の半分以下にする（1回の取得の失敗だけでは警告を出さないため）。この条件は運用上の確認で確かめる（§7 手順 7）
- 時刻表（静的データ）：取得日時を表示する。センターの更新通知から1週間以内に反映する。照合し直すまで公開しない仕組み（§7 手順 7）では、(a) で照合済みの期間を外し、古い内容を表示しないことが「反映」に当たると整理する。これは本サイト側の解釈で、ODPT には確認していない
- 時刻表の鮮度の閾値（取得の失敗が続いたときの上限）：2段階の閾値（環境変数、秒）とする（2026-11-11 運営者決定）。警告の閾値（初期値3日）を超えたら「最終取得から時間が経過しています」を表示し、公開停止の閾値（初期値7日、7日以下）を超えたら公開を止める。TKN 発・TKN 着ごとに、表示するときに判定する。詳細は §7 手順 7（GitHub Issue #11）
- 障害時の表示方針：リアルタイム情報は「更新停止／要公式確認」と表示し、古い状態を表示しない

### 同期・取り込みの実装への申し送り（2026-10-30 PR #5 レビューで追加、未実装・要判断）

- 識別キー：ODPT の `owl:sameAs` には運航日が含まれない（§6）。`FlightOperation` の識別・upsert のキーは「JST の運航日＋便名＋方向」で作る。深夜帯の運航日を、取得時刻の JST 日付で決めるか `dc:date` で決めるかは、日付の切り替わり時刻（§6 未確認点）を観測してから決める。事務局回答（§9 F7、M6）では午前0時過ぎに当日分へ切り替わる動作が現在も同じで、`Yesterday` は JAL 便に使われない。TKN には日付をまたぐ便がないため、「取得時刻の JST 日付」が有力な案。
- 運航会社：`operator_code` は null/unknown とし、`odpt:airline` は別の項目に原文のまま保持する（§4）。項目名と意味を決める。
- 空配列の扱い（パラメータ名の誤りが 200・空配列になるため。§3）。案：
  - クエリのパラメータ名を定数にまとめ、組み立てた URL を Unit テストで固定する。
  - Mapper で、各レコードの空港が TKN と一致するかを検証する。発着情報では `odpt:departureAirport` / `odpt:arrivalAirport`、時刻表（`odpt:FlightSchedule`）では `odpt:originAirport` / `odpt:destinationAirport` を見る。
  - 空配列は即エラーにせず、同期ログに「0件」として残す。時刻表の取得が空なら異常とする。運航情報は、運航時間帯に連続して0件のときだけ警告とする（全便欠航の日に空配列が返る可能性と、`odpt:note` で運航日が限られる便が曜日の時刻表に毎週載っていることを考慮）。
- 鮮度：出発と到着で `dc:date` が異なる（§6）ため、鮮度は種別ごとに判定する。
- リトライ：429 と 5xx だけを指数バックオフでリトライし、403・404 はリトライしない。上限超過時は 429 で、`Retry-After` は付かない（§1、§9 M9）。待ち時間は自前の指数バックオフで決める。`Retry-After` が付いた場合は下記に従う。応答ヘッダー `X-RateLimit-Remaining-*` はログに記録するだけで、待ち時間には使わない（上限値は現状の設定で変わり得るため）。
  - `Retry-After` が付いた場合の扱い（2026-11-12 運営者決定、PR #17）：M9 では付かないとされているため、念のための備えとする。値（秒数、または HTTP の日付から求めた待ち時間）が 0 より大きく20秒以下なら、その時間だけ待ってリトライする。0 以下（待たずに再送してレート制限を連打する形になるため）、または20秒を超える値（cron の実行が長く止まるため）なら、リトライせずに失敗にする。読めない値は無視して、自前のバックオフでリトライする。失敗にした場合は、§7 手順 7 の「取得に失敗した」として扱い、同期は終了コード 1 で終わる
  - 1回の取得の時間の上限は、すべての試行と待ち時間を合わせて120秒とする（HttpClient の `max_duration` は試行全体に効くため）。待ち時間の上限（20秒）と自前のバックオフ（1・2・4秒）を足しても、上限に十分な余裕が残るようにしている
- 呼び出し回数：上限は接続元 IP 単位（§9 M9）。本番 VPS からの呼び出しは、同じ IP の他の処理と上限を共有する。開発・CI は別の IP なので本番の上限を消費しないが、CI から ODPT へ実アクセスはしない（CLAUDE.md §9）。上限値は現状の設定で変わり得るため、コードに固定しない。

### 画面実装への申し送り（2026-10-29 レビューで決定、未実装）

## 10. Go/No-Go 判断

| 対象 | 判断 | 根拠 | 判断日 |

運航状況の自動公開は、利用許諾と必要なデータの両方が確認されるまで有効化しない。

### 公開前の確認事項（時刻表の公開まで。JAL サイト利用規約の確認は Phase 1 MVP の公開前にも必要）
- 規約・基本ライセンス・ガイドラインの原文を、開発者サイトのブラウザ表示で目視確認する（§0 注記）。その際、利用料の定めがないこと、JAL のデータセットに基本ライセンス以外の利用条件が付いていないことを確かめる（§1 未確認点）。食い違いがあれば Go を取り消す
- 本サイトの問い合わせ先を決める（ガイドライン 3.1 の必須の通知に必要）
- 運営者が同期ログを確認する頻度を決める（§7 手順 7）
- 同期の処理そのものが止まったことを、外から検知する方法を決める（§7 手順 7「時刻表の鮮度の閾値」。例：ヘルスチェックで方向ごとの取得の記録からの経過を返し、外部から監視する）
- JAL サイト利用規約で、社名・商標をどう扱うかを確認する（§7 未確認点）。社名を使う公式運航情報の案内文（CLAUDE.md §6）を載せてよいか、`/sources` にデータセット名を書いてよいかを判断する
