- 構造化項目（曜日・`isValidFrom/To`・時刻）だけで「この日の時刻表」を作ると、`odpt:note` に書かれた運航日の限定や時刻変更が反映されず、**運航しない便や誤った時刻を表示する**。`odpt:note` を機械的に解釈するのは表記ゆれがあり危険。
- 対応案（要判断）。どの案にも利用者を誤導する境界がある：
  - 案A「運航日の限定を表す備考の便は表示しない」：実際の運航日（12/28、1/1 など）にもその便が表示されなくなる。
  - 案B「備考あり・要公式確認」を付けて時刻表の時刻を表示する：時刻変更の期間中は誤った時刻が主表示になる（例：JL3794 は 11/16-23 に1時間40分早発で、時刻表の時刻と1時間半以上ずれる）。
  - 案C 備考がある便は時刻表の時刻を確定値として目立たせない（時刻欄を「備考参照」にし、備考の原文を表示する）。
- どの案を選んでも、「運航日限定」（例：12/28・1/1）と「時刻変更期間」（例：11/16-23、12/1-1/4）の初日・最終日・期間外の日付を、境界条件として受け入れ基準に書く。
- **決定（2026-10-30、運営者）：案C を採用する。** `odpt:note` がある便は、時刻欄を「備考参照」とし、備考の原文（`ja`）を表示する。備考の内容は機械的に解釈しない。備考の記法が安定していると運用で確認できた場合に限り、解釈して時刻に反映することを改めて検討する。
  - 備考を解釈しないため、備考で運航日が限られる便（例：JL2470/2471「12/28・1/1・運航」）も、曜日の時刻表に載っている日はすべて表示対象になる。運航しない日を本サイトが判定することはしない。
  - **表示方法（2026-10-30、運営者決定）：備考がある便は、通常の一覧に混ぜず、一覧の下の「備考のある便」の枠にまとめて表示する。** 通常の一覧には備考がない便だけを並べる。枠の見出しには「運航日が限られる、または期間によって時刻が変わる便です。運航日・時刻は備考と公式情報で確認してください。」の趣旨の説明を付ける（文言は画面実装時に確定）。
  - 受け入れ基準（期待する表示）：備考がある便は、備考の期間内・期間外・初日・最終日のどの日付でも「備考のある便」の枠にだけ表示し、通常の一覧には出さない。各行は便名・区間・時刻欄「備考参照」・備考の原文・運航状況欄「運航状況未確認」とする。期間外の日に便を消したり、時刻表の時刻を表示したりしない。
  - 既知の不便：備考はその日に関係があるかどうかに関係なく付いている（例：JL3796「12/1-1/4・10分早発」は 10/29 には通常どおりだが「備考参照」になる）。ODPT の運航情報を表示できるようになるまでの、安全側の暫定表示とする。

### 同期・取り込みの実装への申し送り（2026-10-30 PR #5 レビューで追加、未実装・要判断）

- 識別キー：ODPT の `owl:sameAs` には運航日が含まれない（§6）。`FlightOperation` の識別・upsert のキーは「JST の運航日＋便名＋方向」で作る。深夜帯の運航日を、取得時刻の JST 日付で決めるか `dc:date` で決めるかは、日付の切り替わり時刻（§6 未確認点）を観測してから決める。2022 年時点の事務局回答（§9 F7）では午前0時過ぎに当日分へ切り替わるとされ、TKN には日付をまたぐ便がないため、「取得時刻の JST 日付」が有力な案。
- 運航会社：`operator_code` は null/unknown とし、`odpt:airline` は別の項目に原文のまま保持する（§4）。項目名と意味を決める。
- 空配列の扱い（パラメータ名の誤りが 200・空配列になるため。§3）。案：
  - クエリのパラメータ名を定数にまとめ、組み立てた URL を Unit テストで固定する。
  - Mapper で、各レコードの `odpt:departureAirport` / `odpt:arrivalAirport` が TKN と一致するかを検証する。
  - 空配列は即エラーにせず、同期ログに「0件」として残す。時刻表の取得が空なら異常とする。運航情報は、運航時間帯に連続して0件のときだけ警告とする（全便欠航の日に空配列が返る可能性と、`odpt:note` で運航日が限られる便が曜日の時刻表に毎週載っていることを考慮）。
- 鮮度：出発と到着で `dc:date` が異なる（§6）ため、鮮度は種別ごとに判定する。
- リトライ：429 と 5xx だけを指数バックオフでリトライし、403・404 はリトライしない（上限超過時のステータスは未確認。§1）。
- 呼び出し回数：日次の上限（24000回）は、同じキーを使う開発・CI・本番で共有する前提で同期間隔を決める。

### 画面実装への申し送り（2026-10-29 レビューで決定、未実装）

`/` の現在の実装は、スナップショット全体の取得日時（`fetchedAt`）1つで鮮度を判定している。閾値を超えると、観測した運航状況を「更新停止／要公式確認」に置き換え、変更後（見込み）時刻を表示しない。時刻表データを取り込む前に、次の点を仕様として決める。

- 鮮度の判定を時刻表と運航状況で分ける。時刻表の取得日時（`FlightSchedule.fetched_at`）と、運航状況の観測・取得日時（`FlightOperation.observed_at` / `fetched_at`）を別々に持つ。時刻表だけのデータに、リアルタイム用の閾値をかけない。
- `odpt:note` がある便：案C に決定し、通常の一覧とは別の「備考のある便」の枠に、時刻欄「備考参照」と備考の原文で表示する（§5）。受け入れ基準に、運航日限定・時刻変更期間の境界日付を入れる。

- 同期失敗（データソース障害）の状態を定義する。「未取得」「時間経過」と区別して表示するかどうかも決める。
- Phase 2 では ODPT の `dc:date`（データ生成時刻）を「最終取得」とは別の行に表示する。
- 実績時刻（`actual_*`）を表示するかどうか、表示する場合の列を決める（ODPT の項目確認後）。

  - 到着便画面での「出発済み」の表現
